# MDD — Principles, Abstraction Layers, and Workflow

**Source:** [Model-Driven Development Standard.md](../../../Resources/documents/frameworks/Model-driven-development/Model-Driven Development Standard.md), [Standard/Principles.md](../../../Resources/documents/frameworks/Model-driven-development/Standard/Principles.md), [Standard/Abstraction Layers.md](../../../Resources/documents/frameworks/Model-driven-development/Standard/Abstraction Layers.md), [Standard/Workflow.md](../../../Resources/documents/frameworks/Model-driven-development/Standard/Workflow.md)

---

## Summary

Model-Driven Development (MDD) inverts the normal relationship between models and code: the model is the source of truth; code is a generated by-product. Engineers work in concepts drawn from the problem domain rather than from any specific platform. Automated transformations carry models down through a stack of abstraction layers to running code. The methodology exists to separate what a system means from how one platform implements it, making the meaning reusable when platforms change.

## Why MDD Exists

Hand-written code couples *what the system means* to *how one platform happens to implement it*. When the platform changes — new framework, new database, new runtime — the meaning must be rediscovered and rewritten. Productivity is capped by how fast people can type correct, low-level code (source: Model-Driven Development Standard.md).

MDD attacks both problems. By capturing the system as a model expressed in concepts close to the problem domain, the meaning becomes explicit and reusable. By generating code from that model, the tedious descent to a platform is automated and repeatable: change the model, regenerate; change the target platform, run a different transformation against the *same* model (source: Model-Driven Development Standard.md).

This is the same instinct behind [[../spec-driven-development/sdd-overview|Spec-Driven Development]] — invest in a durable upstream artefact rather than chasing the code — taken one step further: the upstream artefact is formal and machine-transformable, not just structured prose (source: Model-Driven Development Standard.md).

## The Ten Principles

1. **Models are the primary artefact.** The model — not the code — is the source of truth. If a question about the system can only be answered by reading generated code, the model is incomplete. Fix the model, then regenerate; never fix the code and leave the model behind (source: Standard/Principles.md).

2. **Raise the abstraction level.** Work in concepts drawn from the *problem* domain, not the *solution* platform. A clinician's model talks about patients, encounters, and dosages — not foreign keys, REST endpoints, and thread pools (source: Standard/Principles.md).

3. **Separate concerns by layer.** Keep domain meaning (PIM) independent of platform detail (PSM). The value is in the boundaries: a PIM kept free of platform assumptions can be re-targeted when platforms change (source: Standard/Principles.md).

4. **Automate the descent.** The journey from abstract model to running code should be carried by automated transformations, not by people retyping the same information at each level. A transformation run a hundred times pays back the effort of writing it once (source: Standard/Principles.md).

5. **Every model conforms to a metamodel.** A model is only as precise as the language it is written in — and that language is itself a model (a metamodel). Conformance is what makes models machine-processable: a tool can validate, query and transform a model only because it knows the metamodel the model obeys (source: Standard/Principles.md).

6. **Generate, don't hand-edit below the line.** Generated code must be protected from manual edits or the model stops being the source of truth. Two patterns: full generation (the output is disposable and never touched) or protected regions (clearly marked hand-written blocks preserved across regenerations) (source: Standard/Principles.md).

7. **Transformations are first-class assets.** A transformation is software — it has inputs, outputs, edge cases, and bugs. Version it, test it against known model/output pairs, review changes to it, and reuse it across projects (source: Standard/Principles.md).

8. **Portability through platform independence.** A PIM with no platform assumptions survives a platform change: re-point it at a new transformation and regenerate. The discipline is constant vigilance against platform detail leaking upward into the PIM (source: Standard/Principles.md).

9. **The right language beats a general one.** A domain-specific language (DSL) is narrow but sharp: it lets domain experts read (and write) models, rejects nonsensical constructs by design, and produces cleaner generators. Stretching UML to cover a specialised domain often costs more than defining the small language the domain actually needs (source: Standard/Principles.md).

10. **Models are living documents.** When the system changes, the model changes first and the code follows by regeneration. A model that lags behind the running system lies with authority (source: Standard/Principles.md).

## The Abstraction Layers: CIM, PIM, PSM

These three layers come from the OMG's Model-Driven Architecture (MDA) and are the standard vocabulary in MDD (source: Standard/Abstraction Layers.md).

```
CIM ──(refine)──▶ PIM ──(transform)──▶ PSM ──(generate)──▶ Code
 │                 │                     │                   │
domain           solution             platform            running
concepts         structure            detail              system
```

**CIM — Computation-Independent Model.** Describes the system in the language of the business domain with no assumption that software is even involved. Audience: domain experts. Answers "what is this world made of and how does it behave?" (patients and prescriptions, orders and shipments — not classes or endpoints). Example: "An order is placed by a customer, contains one or more line items, and cannot be shipped until paid" (source: Standard/Abstraction Layers.md).

**PIM — Platform-Independent Model.** Describes the computational aspects of the system — structure, behaviour, operations — without reference to any specific technology. Commits to the system being software, but not to *which* software stack. A PIM defines an `Order` class, its attributes, its state machine, and its operations, while saying nothing about Java vs Python, SQL vs document store, or REST vs gRPC (source: Standard/Abstraction Layers.md).

**PSM — Platform-Specific Model.** The PIM plus all the decisions the PIM withheld: which entity framework, which annotations, which REST conventions. Usually one PSM per target platform, all derived from the same PIM. This is where `Order` becomes a `@Entity` JPA class mapped to an `orders` table (source: Standard/Abstraction Layers.md).

**Code.** The PSM is generated into source code (and configuration, schema, etc.). In a fully model-driven flow this is automatic and the output is not hand-edited.

## The Metamodel Hierarchy: M0–M3

Orthogonal to the refinement stack. Answers: "in what language is each model written, and what governs that language?" (source: Standard/Abstraction Layers.md)

| Layer | Name | Contains | Example |
|---|---|---|---|
| **M3** | Meta-metamodel | The language for defining metamodels | MOF (Meta-Object Facility) |
| **M2** | Metamodel | The language for defining models | The UML metamodel; a custom DSL metamodel |
| **M1** | Model | Your model of the system | A specific UML model of Order, Customer |
| **M0** | Instance / data | The real-world objects | Order #4711 placed by Alice at 14:32 |

Key properties:
- **Strict conformance.** Every element at every layer corresponds to an element of the layer above.
- **M3 is self-describing.** MOF is defined in terms of itself, stopping the tower from needing infinite layers.
- **UML lives at M2.** The UML metamodel is the most prominent M2 model. When you draw a class diagram you are working at M1, in a language defined at M2.

**How the two stacks meet.** CIM, PIM, and PSM are all M1 artefacts — models of *your* system. What differs between them is how abstract they are about the system, not which metamodel layer they occupy. The metamodel hierarchy gives machine-processability; the refinement stack gives portability (source: Standard/Abstraction Layers.md).

## Why Both Stacks Matter

Tools can validate, query, and transform models *only because* of the metamodel hierarchy — a transformation engine reads a model at M1 by knowing its metamodel at M2. And teams get portability *only because* of the refinement stack — a PIM kept free of platform detail can be transformed to many PSMs. Lose the discipline in either stack and MDD degrades into drawing pictures that no tool can use and no platform change can survive (source: Standard/Abstraction Layers.md).

## Family of Acronyms

| Acronym | Scope | Pins down |
|---|---|---|
| **MBE** | Broadest | Models are *used* in the process, but need not drive it |
| **MDE** | Broad | Models *drive* the whole engineering lifecycle, including non-code concerns |
| **MDD** | Software development | Models drive the building of running software |
| **MDA** | Specific | OMG's standardised flavour of MDD (CIM/PIM/PSM, UML, MOF, QVT) |

This reference's subject is MDD; MDA is its most formal, standardised interpretation (source: Model-Driven Development Standard.md).

## Key Takeaways

- MDD inverts the usual relationship: model is primary, code is output. When the system changes, the model changes first.
- The refinement stack (CIM → PIM → PSM → Code) gives portability by keeping domain meaning separate from platform detail.
- The metamodel hierarchy (M0–M3) gives machine-processability by ensuring every model is written in a governed language.
- Both stacks are required: lose either and MDD becomes diagram-drawing.
- The core tension to maintain: no platform detail in the PIM. If a sentence in your PIM names a framework, database, or wire format, it belongs in the PSM instead.
