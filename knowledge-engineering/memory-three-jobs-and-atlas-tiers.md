# Memory's three jobs — storage, injection, recall — and Atlas's tier adoption

**Source:** [I Built The Best Claude Memory System (Beats Hermes)](https://www.youtube.com/watch?v=H9BUkgDf5Y4)
**Author:** Simon Scrapes (YouTube)
**Companion sources:** session capture 2026-06-11 (implementation outcome), engine-boundary capture 2026-06-11

---

## Summary

Simon Scrapes' video decomposes agent memory into three jobs — storage, injection, recall — and assembles a "best of each framework" system inside Claude Code from Hermes, Memarch/MemSearch and GBrain parts (source: transcript-i-built-the-best-claude-memory-system.md). Atlas was benchmarked against this framework on 2026-06-11: the engine's governance already exceeded the video's system, but three gaps (fuzzy recall, agent-decided capture, no session-start content) were adopted as a tiered memory model in the agentic-knowledge-engine boilerplate and propagated to Atlas (source: session-2026-06-11-1307.md).

## The three-jobs framework

Every memory system makes a choice per job (source: transcript-i-built-the-best-claude-memory-system.md):

- **Storage** — who triggers the save (hook vs agent-decided) and what form it takes (verbatim vs summarized). Claude Code out of the box is agent-decided + summarized, which is "leaky": unflagged facts are never saved.
- **Injection** — hook-loaded (guaranteed) vs agent-pulled, and whether a character cap keeps it lean. Stock Claude Code hook-loads CLAUDE.md + memory index but is unbounded.
- **Recall** — keyword vs semantic vs hybrid search. Stock Claude Code has "basically no search at all"; the only fallback is resuming the original session.

His picks: MemSearch-style automatic per-turn capture hook summarized by Haiku into a daily log; a Hermes-style frozen session-start snapshot (identity, profile, recent memories, ~1,300 tokens, cached); Memarch local vector indexing with hybrid keyword+semantic search, layered with GBrain's reranking and cited synthesized answers in a multi-tier flow that checks injected memory first and searches deeper only on a miss (source: transcript-i-built-the-best-claude-memory-system.md). Rejected options: Hermes raw-transcript capture (too bulky), GBrain full knowledge-graph extraction (overkill for a small business), Hermes keyword-only recall (source: transcript-i-built-the-best-claude-memory-system.md). For teams he sketches a GBrain-inspired "company brain": one shared Postgres/Supabase store with row-level security scoping each user's slice (source: transcript-i-built-the-best-claude-memory-system.md).

## Atlas comparison — verdict: no rebuild

Atlas's harness (frozen schema, drift audit, eval harness, per-claim citations, quarantine, episodic memory) is stronger governance than the video's system, which has no measurement layer at all; the comparison confirmed "governance > feature count" as the design philosophy (source: session-2026-06-11-1307.md). Three genuine gaps were adopted:

1. **Tier 0 — session snapshot.** `_episodes/snapshot.md` (~750 tokens seeded, ≤1,500 cap), regenerated by `reflect`, injected by a SessionStart hook — identity plus recent decisions available with zero file reads (source: session-2026-06-11-1307.md).
2. **Tier 2 — hybrid search.** `Intelligence/_search/` local SQLite index (FTS5 + sentence-transformers embeddings, reciprocal-rank fusion): 599 articles, 5,531 chunks at rollout; zero-keyword-overlap queries verified (e.g. "how should I sound" routed to the writing-rules article). Results are routing pointers, never citation sources; the tier-1 index walk stays the primary path. FTS-only graceful fallback when embeddings are unavailable — stability over perfect recall (source: session-2026-06-11-1307.md).
3. **Deterministic capture.** A SessionEnd hook summarizes durable signals into `Resources/context/` — the differentiator vs naive logging is that it is silent on mechanical sessions (source: session-2026-06-11-1307.md).

## Engine boundary rule

Core memory/intelligence features belong in the public agentic-knowledge-engine boilerplate, which Atlas instances inherit; `Tasks/` and `Dashboard/` are Atlas-only add-ons "not even contemplated in the Atlas memory engine" and must not be integral to engine improvements. `Skills/` holds only skill definitions — tooling scripts live in self-contained governance zones like `Intelligence/_search/`. Hook install instructions live in the boilerplate README, the engine's public face on GitHub (source: 2026-06-11-engine-core-vs-atlas-addons.md). Pushes to the public boilerplate repo happen only on Max's explicit request ("publish") — agents don't push the engine to GitHub on their own initiative (source: session-2026-06-11-1459.md).

## Key Takeaways

- Storage / injection / recall is a useful audit lens: Atlas failed it only on recall fuzziness, capture determinism and session-start content — all bounded add-ons, no rebuild.
- Multi-tier recall (snapshot → index walk → hybrid search) keeps the cheap layer answering first; search returns pointers so the citation discipline survives.
- The video's system lacks any eval/measurement loop — Atlas's `evaluate` verb (q42/q43 fuzzy-phrasing questions, `tier_used=` tracking) is the part worth keeping proprietary to the methodology.
- Engine improvements land in the public boilerplate first; Atlas consumes them. Add-ons stay out of the core.
